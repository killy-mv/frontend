Store things

Four storage systems, four different shapes. Press a button, then follow the How to see it steps to watch the browser actually write to disk.

Keep DevTools open on the Application tab while you work (F12 → Application; Firefox calls it Storage).

1 Cookies

A few kilobytes of text that the browser attaches to every request on its own. That automatic attachment is the whole point — it is how a stateless protocol remembers who you are. The interesting part of this demo is the HttpOnly cookie: the browser stores it and sends it, but document.cookie cannot see it.

How to see it
  1. Open DevTools → Application → Storage → Cookies → http://localhost:5180.
  2. Press Ask the server to set cookies. Three rows appear that you never wrote — the server sent Set-Cookie headers and the browser filed them away.
  3. Look at the HttpOnly column. session is ticked; the other two are not.
  4. Press Read with JavaScript — only two come back. Then press Ask the server what it sees — all three. Same jar, two different views.
  5. Open the Network tab, press Ask the server what it sees again, click the request and look at the Cookie: request header. You never wrote that header.

      


      
      

        
2 localStorage

        

          A synchronous key–value map holding roughly 5 MB of strings only. Everything
          else has to be encoded first — an object becomes JSON, and a file becomes a base64 data
          URL, which is what the file button below does. Storing a file here is possible but wasteful:
          base64 inflates bytes by about a third, so a 4 MB image will not fit.
        


        

          How to see it
          
    
            
  1. DevTools → Application → Local Storage → http://localhost:5180.
    2. 
            
  2. Press Save a note and watch the row appear in the table live. You are watching a write to disk.
    3. 
            
  3. Pick a small image with Choose file, then press Store the file. The value column fills with data:image/png;base64,… — the file as one very long string.
    4. 
            
  4. Press Restore the file to turn that string back into a picture.
    5. 
            
  5. Now the persistence proof: quit the whole browser, not just the tab. Reopen it, come back here and press List everything. It all survived, because it was written to a LevelDB file in your browser profile.
    6. 
            
  6. Press Fill until full to hit the quota and see the QuotaExceededError that a real app has to handle.
    7. 
          

        


        

          
          
          
          
          
          
        

        

          
          
          
        

        

        

      


      
      

        
3 IndexedDB

        

          The real database: asynchronous, transactional, hundreds of megabytes, and it stores
          structured objects rather than strings. Its vocabulary is slightly different from SQL —
          an object store is the table, a key path is the primary
          key, and an index is the field you want to search by. Schema changes only
          happen inside onupgradeneeded, which fires when you open the database with a
          higher version number. That is a real migration, and the buttons below run one.
        


        

          How to see it
          
    
            
  1. DevTools → Application → IndexedDB.
    2. 
            
  2. Press Create v1, then expand browser-storage-demo in the sidebar. A books store appears with indexes by_author and by_year under it. Those are your tables and fields.
    3. 
            
  3. Press Add 3 books and click books in the sidebar — the records are listed as expandable objects, not text.
    4. 
            
  4. Press Migrate to v2. A second store authors appears and books gains a by_title index. The version number next to the database name changes from 1 to 2. (Hit the refresh icon in the DevTools panel if the tree looks stale.)
    5. 
            
  5. Press Query by index to fetch records by author without scanning the store.
    6. 
          

        


        

          
          
          
          
          
          
          
        

        

      


      
      

        
4 Cache API

        

          The only storage that holds whole HTTP responses — status, headers and body —
          keyed by the request that produced them. This server hosts a small four-file site at
          /mini-site/; the buttons below fetch it over the
          network and keep a copy. Register the service worker afterwards and the site loads with
          your network switched off entirely.
        


        

          How to see it
          
    
            
  1. Open /mini-site/ once so you know what it looks like, then come back.
    2. 
            
  2. DevTools → Application → Cache Storage.
    3. 
            
  3. Press Fetch & cache the mini-site. A cache named mini-site-v1 appears with four entries. Click one — you get the response headers and body, not just a value.
    4. 
            
  4. Press Read from cache. The content is returned with no network request at all — check the Network tab and you will see nothing new.
    5. 
            
  5. The payoff: press Register service worker, then set Network → throttling to Offline, then open /mini-site/. It loads normally. You can even stop the server (Ctrl+C) and it still loads.
    6. 
            
  6. Press Unregister & delete, go back online, and reload to return to normal.
    7.
