Talk to the network

Three ways a page can move bytes, in order of how much freedom they give it: ask and wait, keep a channel open, or cut the server out altogether. Press a button, then follow the How to see it steps.

Keep DevTools open on the Network tab (F12 → Network), and keep the terminal running npm start visible — half of what happens here is only observable from the server side.

signalling socket: connecting…

1 fetch

One request, one response, and the connection is finished. The parts worth knowing are the ones that are easy to never use: a response body is a stream, not a lump, so you can read it while it is still arriving; and a request is cancellable, which really does close the socket rather than just ignoring the answer. Note the asymmetry at the end — fetch can report download progress but not upload progress, which is the one reason XMLHttpRequest is still written in 2026.

How to see it
  1. Press Plain fetch, then look at the Network tab: one row, request and response, done.
  2. Press What did the browser send?. You set none of those headers — User-Agent, Accept, Sec-Fetch-* were all added under you.
  3. Press Read the body as it arrives and watch the lines appear one at a time. Compare with Wait for the whole body, which prints nothing for three seconds then everything at once. Same endpoint, same bytes.
  4. Press Download 4 MB with progress. The percentage only exists because the server sent Content-Length; the bar is received / total, counted by hand from the stream.
  5. Press Start a slow request, then Abort it — and now look at the terminal. The server prints that the socket closed. Cancelling is not "ignore the reply", it tears the connection down.
  6. Press Abort after 1s (timeout) — same mechanism, but AbortSignal.timeout() instead of a manual controller.
  7. Press Upload 4 MB with progress twice: once as fetch, once as XHR. Only one of them can tell you how far it got.

      


      
      

        
2 WebSocket

        

          The connection stays open and either side may send at any time. It begins as an
          ordinary HTTP request carrying Upgrade: websocket; the server answers
          101 Switching Protocols and from that instant there is no more HTTP on the
          socket, just frames. The capability that has no equivalent above is server
          push: press Start the ticker and messages arrive that this page
          never asked for.
        


        

          How to see it
          
    
            
  1. DevTools → Network → filter WS → click the ws row. The Headers tab shows the 101 handshake, and Messages shows every frame live, green for sent and white for received.
    2. 
            
  2. Press Echo a few times, then Start the ticker and stop clicking. Frames keep arriving. Nothing on this page requested them.
    3. 
            
  3. Open this page in a second tab, then press Broadcast to other tabs. The message appears in the other tab's log — through the server, to a different browsing context.
    4. 
            
  4. Press Send binary. The server reverses the bytes and sends them back; the log shows both directions as hex. No JSON, no base64.
    5. 
            
  5. Press Server ping. Nothing appears in Messages for the ping itself and no event fires here — the browser answers the pong on its own, the same way it attaches cookies. The RTT comes back afterwards as a normal message.
    6. 
            
  6. Press Flood 10 MB and watch bufferedAmount climb and drain. send() never blocks and never fails when you are too fast; it queues, in memory, forever. That number is the only warning you get.
    7. 
            
  7. Press Ask the server to close. The close code is 4000 with a reason string — application close codes start at 4000 and are yours to define.
    8. 
          

        


        

          
          
          
          
          
        

        

          
          
          
          
          
          
        

        

      


      
      

        
3 WebRTC data channel

        

          The one that is genuinely different in kind: after a handshake brokered by the server, the
          two browsers connect directly to each other and the server leaves the
          path. It is not a protocol you send messages over — it is a negotiation. Each side
          describes itself in an SDP offer or answer, then both collect
          ICE candidates (every address they might be reachable at) and try them in
          pairs until one works.
        


        

          How to see it
          
    
            
  1. Open this page in a second tab. Nothing here works with one. The strip at the top must say connected in both — the WebSocket from panel 2 is the signalling channel.
    2. 
            
  2. In this tab press Start the connection. The other tab answers by itself. Read both logs side by side: offer → answer → candidates → connected.
    3. 
            
  3. Type something and press Send. It appears in the other tab. Check the Network tab — nothing was requested. There is no row, because there is no server involved.
    4. 
            
  4. The payoff. Press Disconnect in panel 2 — or stop the server entirely with Ctrl+C — and keep sending. It still works. The signalling server was only ever needed for the introduction.
    5. 
            
  5. Press Send 8 MB and read the throughput. Those bytes never touched Node.
    6. 
            
  6. Press Show the chosen route for the candidate pair that won. On one machine both ends are host candidates — your loopback and LAN addresses.
    7. 
            
  7. Tick Use a STUN server and start over. New candidates appear of type srflx — that is your public IP, discovered by asking a stranger. Which is also why WebRTC is a fingerprinting concern.
    8. 
          

        


        

          
          
          
          
        

        

          
          
          
        

        

        

      


      

        

          The ladder is about who is allowed to speak first. With fetch only the page can;
          with a WebSocket either end can; with WebRTC there is no longer an "end" in the middle at
          all. Each step costs something — a held-open connection, then a negotiation that can fail
          for reasons no server log will explain.
